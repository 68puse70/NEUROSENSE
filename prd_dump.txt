Sensor Monitoring & Session Analytics Web Application
Version 1.0  |  9 October 2026  |  Status: Draft
A local-first web dashboard for live sensor monitoring, calibration,\nsession recording, and future-ready data analysis.
1. Document Overview
This PRD defines the first version of NeuroSense, a browser-based dashboard for viewing, recording, and reviewing data from a sensor-equipped prototype. The initial setup is expected to use an ESP32 with FSR and flex sensors. The application should be developed with simulated data first, then connected to the real device when firmware output is ready.
2. Problem Statement
Raw sensor readings are difficult to interpret when they are only available in a serial monitor. The team needs one interface that can show live readings, highlight connectivity problems, help calibrate sensors, and save sessions for later review. A web app provides a flexible interface without requiring a separate desktop application.
3. Product Goals
Display live sensor readings and connection status in a clear, responsive interface.
Plot sensor values over time to make changes and anomalies easier to observe.
Allow users to start, stop, name, save, and review recording sessions.
Persist time-series readings and session summaries locally.
Provide a guided calibration workflow and store calibration settings.
Start with simulated sensor data and later switch to ESP32 data with minimal UI changes.
Keep the architecture extensible for future sensors and ML-based analysis without promising those features in V1.
4. Non-Goals for V1
A native Android/iOS application; the web interface should work on mobile browsers.
Cloud accounts, multi-user permissions, remote access over the public internet, or cloud synchronization.
Medical diagnosis, clinical monitoring, or claims that readings represent validated physiological measurements.
Automatic gesture classification or AI predictions.
Advanced analytics, multi-device fleet management, or production-grade deployment.

8. Functional Requirements
8.1 Live dashboard and sensor monitor
Display one card per configured sensor, using a stable sensor ID and editable display name.
Show the latest value, last-update time, and a clear status such as Connected, Stale, or Unavailable.
Where firmware supports it, show raw ADC reading separately from filtered and normalized values; never imply a derived value exists when it does not.
Render a time-series chart with selectable sensors and a readable time axis.
Show device connection status and distinguish “no device”, “connected but stale”, and “receiving data”.
Use simulated data mode as a visible, explicit mode so test readings cannot be mistaken for real hardware data.
8.2 Recording and storage
Provide Start Recording and Stop Recording controls with clear state feedback.
Allow an optional session name and notes; generate a unique session ID automatically.
Store each reading with a timestamp, session ID, and sensor values (or a consistent per-sensor record model).
Store session metadata including start/end time, duration, sample count, sensor configuration, and whether the source was simulated or hardware.
Save data incrementally so a browser refresh or temporary UI issue does not discard the entire active recording.
Warn before destructive actions such as deleting a saved session.
Allow a saved session to be opened later and its data exported as CSV.
8.3 Calibration
Allow a user to select a sensor and capture a baseline/reference reading.
Support a minimum/maximum or baseline/reference range where appropriate for the sensor type.
Preview the resulting normalized value before saving calibration.
Store calibration settings with a version or timestamp and associate the settings used with recorded sessions.
Clearly label calibration as prototype calibration, not medical calibration.
8.4 History and analytics
List sessions newest-first with name, timestamp, duration, sample count, and data source.
Provide empty, loading, and error states.
Show per-session minimum, maximum, mean, and sample count where calculation is meaningful.
Allow CSV export with headers, timestamps, and stable sensor identifiers.
Keep chart axes and units consistent and indicate missing samples or gaps where practical.
8.5 Settings
Allow configuration of device endpoint or connection method.
Allow sensor labels and mapping to physical sensors to be edited.
Show current application mode: simulated or hardware.
Provide a way to view the active sensor schema and calibration values.
Avoid exposing secrets; the initial local prototype should not require user credentials.
9. Proposed Technical Architecture
Recommended initial stack: React + Vite for the frontend, Tailwind CSS for styling, Python FastAPI for the backend, WebSocket for live updates, and SQLite for local persistence. These are proposed choices rather than fixed requirements.
9.1 Data flow
ESP32 → local network/device adapter → FastAPI → (a) WebSocket updates to the browser and (b) timestamped persistence in SQLite. The browser should not write directly to SQLite. Simulated readings should use the same internal data format as hardware readings.
9.2 Suggested API contract (initial proposal)
Endpoint names are illustrative and may be revised during implementation. The ESP32 payload format, sampling rate, sensor count, and connection protocol must be confirmed with the firmware before integration.
10. Data Model
For efficient charting and export, implementation may store readings in a wide format (one row per timestamp with sensor columns) or a normalized format (one row per sensor per timestamp). Choose one deliberately, document it, and ensure CSV exports are easy to analyse.
11. UX / Visual Design Requirements
Use a clean, technical interface with a dark theme as the default design direction and a restrained teal accent.
Keep the main dashboard readable at laptop resolution and usable on mobile browsers.
Use status text/icons as well as colour; colour alone must not convey connection or alert state.
Prioritize live values, recording controls, and connection health above decorative visuals.
Show loading, no-data, disconnected, stale-data, and error states explicitly.
Keep the hand visualisation optional until sensor-to-finger mapping is confirmed.
12. Non-Functional Requirements
13. Acceptance Criteria
With simulated mode enabled, the dashboard displays changing values for all configured sensors.
The UI clearly indicates whether data is simulated, live, stale, or unavailable.
A user can start a named session, observe live readings, stop it, and find it in session history.
Recorded readings survive a page refresh and backend restart under normal local operation.
A user can open a past session and see its recorded time-series chart.
A user can export a session to CSV and verify timestamps and sensor columns/IDs.
Calibration values can be saved and reloaded, and the UI explains which values are raw versus normalized.
When hardware is disconnected or data stops arriving, the UI reports the issue rather than silently showing old values as live.

16. V1 Definition of Done
V1 is complete when the user can run NeuroSense locally, view simulated or real sensor readings, see connection health, record a session, persist it in SQLite, reopen it from history, inspect charts, export CSV, and save basic calibration settings. All screens must distinguish real device data from simulation, and the core flow must work without a cloud account.
