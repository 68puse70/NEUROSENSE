NEUROSENSE
Design Document
UI/UX, Interaction Patterns & Visual System
Version 1.0  |  9 October 2026  |  Companion to the Dashboard PRD
A practical design blueprint for the NeuroSense sensor-monitoring\nweb application and its live data workflows.
1. Design Intent
NeuroSense should feel like a focused engineering instrument: precise, calm, responsive, and easy to read while testing hardware. The interface should make the most important information—sensor readings, device health, and recording state—visible immediately. It should look modern and technical without sacrificing clarity for decoration.
2. Brand & Visual Direction
Recommended direction: “Precision Lab”. Use a deep navy background, slightly lighter panels, cool white text, and a restrained teal accent. Reserve status colours for actual system states. The result should feel suitable for a hardware prototype and future sensor analytics—not like a consumer fitness app.
Colour values are starting tokens, not a substitute for contrast testing. Do not use accent or status colour as the only indicator; pair it with text or an icon.

5. Page-by-Page Design
5.1 Dashboard overview
Purpose: answer “Is the system working, what are the sensors reading, and am I recording?” within a few seconds.
Top row: device connection, data source, active sensor count, and recording state.
Sensor grid: one card per configured sensor with sensor name/ID, latest value, unit or “raw ADC”, optional normalized percentage, and freshness/status.
Live chart: selectable sensors, visible time window, pause/resume display, and clear legend. Avoid plotting incompatible units on the same axis unless the chart clearly communicates separate scales.
Recording controls: Start, Stop, session name, and optional notes. Show a clear active-recording indicator and elapsed duration.
Recent sessions: a compact list of recent recordings with a link to full history.
Empty state: explain how to enable simulation or connect a device; never show fabricated zero values as if they were real.
5.2 Live Monitor
Designed for debugging rather than presentation.
Show raw, filtered, and normalized readings only when each value is available.
Include last update time, sensor ID, configured type, and status.
Use compact sensor rows or cards; let the user select which sensors appear in the chart.
Stale values remain visible for debugging but are visibly marked stale.
5.3 Sessions / History
Use a searchable or filterable table/list with session name, date, duration, source, sample count, and actions.
Opening a session shows metadata, charts, summary statistics, notes, and export controls.
CSV export is a clear secondary action; deletion is separated and requires confirmation.
Differentiate an unfinished/interrupted session from a successfully completed recording if the backend can detect it.
5.4 Calibration
Use a step-by-step flow: choose sensor → capture baseline/reference → preview mapping → save.
Display the current live reading beside the capture action so users can see whether the sensor is responding.
Explain the expected physical action in plain language, e.g. “Leave the sensor relaxed, then capture baseline.”
Show the current saved calibration and when it was last updated.
Provide Cancel and Reset actions; confirm before overwriting calibration.
Do not imply that a simple min/max mapping is a scientifically validated pressure or bend measurement.
5.5 Settings
Group settings by Device Connection, Sensor Configuration, Display, and Data.
Show a connection test result with an explanation and timestamp.
Use stable sensor IDs internally; renaming a sensor should not break old session data.
Clearly show whether changes apply immediately or require reconnect/restart.

9. Accessibility & Readability
Maintain WCAG-aware text contrast, especially for muted metadata and status labels.
Use keyboard-accessible controls and visible focus indicators.
Provide accessible names for icon-only controls and chart toggles.
Do not communicate state by colour alone; include labels such as “Stale” or “Disconnected”.
Respect reduced-motion preferences; live charts should not use unnecessary animations.
Use sufficiently large touch targets on mobile and avoid dense controls next to destructive actions.
10. Charts & Data Visualisation Rules
Show units or explicitly label values as raw ADC / normalized percentage.
Display the selected time range and keep time formatting consistent.
Use stable colours per sensor within a chart session and a visible legend.
Do not smooth or interpolate missing readings in a way that implies measurements were received.
If chart display is downsampled for performance, preserve the original stored readings for export.
Provide a way to pause visual updates without silently stopping recording.
Show gaps or stale periods where practical rather than drawing a misleading continuous line.

12. Implementation Notes for Design-to-Code
Build reusable components rather than separate one-off cards for each sensor.
Drive the UI from sensor configuration so adding/removing a sensor does not require redesigning the page.
Keep display state (selected chart sensors, chart window) separate from recording/storage state.
Use a shared connection-state model so all pages display consistent status.
Build simulation mode through the same reading interface used by hardware data.
Keep visualisation components independent from the ESP32 protocol and database implementation.
Add loading, error, empty, stale, and disconnected states before calling a screen complete.
13. Design Review Checklist
Can a user identify simulated versus hardware data immediately?
Can a user tell if the sensor stream is stale or disconnected?
Can a user start and stop a session without ambiguity?
Are raw and normalized readings clearly differentiated?
Can saved sessions be found, reopened, and exported?
Do screens work with a different number of sensors?
Are empty/error/loading states designed, not left blank?
Can core workflows be completed using a keyboard and on mobile?
Does every critical action provide appropriate confirmation or feedback?

Signal over decoration | Prioritize readings, charts, timestamps, and device state over large illustrations or ornamental effects.
Clear state at all times | Users can tell whether the source is simulated or hardware, whether data is fresh, and whether a recording is active.

Progressive disclosure | Keep the overview simple; put raw diagnostics, detailed summaries, and calibration controls on their own pages.

Pattern | Design rule
Primary action | One visually prominent action per panel, such as Start Recording or Save Calibration.
Destructive action | Use a confirmation step and state exactly what will be deleted or reset.
Connection status | Use text + icon + colour, with last-seen time when disconnected or stale.
Recording state | Show “Recording” and elapsed duration; prevent accidental double-starts.
Chart selection | Sensor toggles update the chart immediately and keep the legend in sync.
Loading state | Use a lightweight skeleton or spinner with context, not a blank panel.
Error state | Explain what failed, likely cause if known, and the next action.
Success feedback | Confirm saved session/export/calibration without blocking the workflow.
Units and labels | Never make users infer whether a number is raw ADC, normalized %, or another unit.

Desktop ≥ 1200 px | Expanded sidebar; 3–5 sensor cards per row as space allows; chart and summary panels can share a row.
